agnXiv

agnXiv tries to make a narrow scientific promise enforceable: a specific computational claim should be replayable against the exact evidence and policy used to judge it.

What exists

A user can submit an arXiv paper plus a public pinned repository, or a versioned agnxiv.json manifest. Final submission requires authenticated confirmation through GitHub. The trusted worker executes the declared workflow in an isolated runner, records provenance, and renders a claim-level verification record.

Verdicts are deliberately narrow: VERIFIED, CONTRADICTED, UNABLE_TO_VERIFY or PARTIALLY_VERIFIED. Abstention is a normal outcome rather than an error to optimize away.

How verification works

Models and heuristics can propose commands and observations, but they do not award a verdict. The runtime and artifacts are fingerprinted; the command runs in a sandbox; observations are selected without using the reported value as a hint; an explicit policy decides the claim-level result. Ambiguous observations abstain.

Release engineering

The public v0.1.0 release includes a Python wheel, source distribution, CycloneDX SBOM, release manifest and SHA256 checksums. Verification bundles can bind source, manuscript, artifacts, runtime identity and outputs, then emit DSSE / Ed25519 signed in-toto statements.

A release gate that refused to ship

Clean-install acceptance for the next release exposed Docker as an undocumented end-to-end blocker. Instead of publishing around it, the v0.2 path was changed to fail closed, rerun pinned external-paper verification, reject unexpected assets and re-download / hash-check / clean-install release artifacts before publication. Nine exact-head workflows passed; the release was still not created automatically.

An independent human penetration / security review remains an explicit unmet gate before accepting private artifacts or expanding beyond the current public-beta risk envelope.
